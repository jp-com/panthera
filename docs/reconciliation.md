# Refunds and inventory reconciliation

Issue refunds in the Stripe Dashboard; this application does not initiate refunds. Register signed snapshot webhook events refund.created, refund.updated, refund.failed and charge.refunded alongside the existing Checkout events. The refund handler retrieves the PaymentIntent, checks PANTHERA metadata, locks the corresponding order, fetches all refunds for the payment, sums succeeded refunds only, and updates recorded payment status. It queues a notification when the settled refund total increases. Full refunds cancel unshipped orders; shipped history is preserved. Physical stock is never automatically increased on refund. Confirm returns, damage and stock counts before adjusting inventory in admin.

Admin reconciliation lists overdue held reservations and discrepancies between inventory reserved and held quantity. A verified live Stripe session can be rechecked manually via the admin API. A paid session consumes stock and records payment once; a confirmed expired unpaid session with no payment intent or a confirmed canceled zero-received intent can release stock. A signed async failure can also release after terminal state verification. Unknown or processing states stay held. No-linked-session cases and mismatches require human review; do not guess from expiry timestamps. The existing confirmation and dispatch outbox still requires a delivery worker. Refund email templates are ready but no messages are sent.

Remaining gates: Stripe restricted key read access for PaymentIntents, Checkout Sessions and Refunds, signature verification in production, live webhook registration, full integration tests including concurrent/duplicate/out-of-order events, dispute handling and risk review, separate database roles, audit migration, rate limits and reconciliation alerting. No real Stripe payments or refunds were performed. Admin mutations are disabled until configured. No automatic cron was installed.
