# Transactional email
Templates are implemented and provider independent. No provider API is called. The existing payment and dispatch handlers already enqueue order_confirmation and dispatch jobs in commerce.notification_outbox within their database transactions. Refund and internal notifications require their own verified event/outbox integration; templates alone do not enqueue them.

Provision Resend through Vercel Marketplace on the original panthera project. Verify a dedicated sending domain or subdomain using Resend's current DNS instructions. Confirm the From and support Reply-To address. Store the API key server-side only. Provider account and sender identity are not yet connected. Do not turn on email delivery during development.

Worker requirements: authenticated production-only invocation, claim jobs using row locks and durable leases, fetch order snapshots from Neon, verify each job's payment/fulfilment state, use provider idempotency keys, record provider message ID and send time, retry transient failures with bounded backoff and stop/alert on permanent failures. Avoid retries beyond provider idempotency window without reconciliation. Do not expose customer contact data in logs. Support internal recipient configuration separately. Refund messages must follow verified Stripe refund events, not manual assumptions. Customer tracking links require an authenticated or unguessable capability-based status endpoint; current dispatch template gives carrier and tracking reference only. Configure scheduled worker only after provider connection and test delivery. No real messages sent.
